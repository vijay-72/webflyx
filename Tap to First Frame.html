Tap to first frame

How a React Native app gets from a tap on its icon to its first useful frame on an Android device, and how to make that happen sooner. Written for a team that ships a settings app on hardware it controls, running React Native 0.72 with the New Architecture.

Your first React frame appears when the slowest thing it depends on finishes. A free main thread is necessary, but it is not enough.

Most startup advice tells you to move work off the main thread. That fixes only half of the problem. A React Native screen waits for a chain of prerequisites: the process, the React runtime, your JavaScript, every native module the screen calls, and the data it shows. Work on a background thread still delays the screen if the screen waits for its result. This guide teaches the chain from the bottom up, so that you can see which link is slow in your app and remove it.

Part 1 of 7 · Explanationabout 12 minutes

The machine: processes, threads, and frames

Before React Native can do anything, Android has to create a process, run code on its main thread, and draw a frame. This part explains those three things from the ground up.

In short

  • Your app is a Linux process. Android creates it by copying a template process called zygote.
  • One main thread runs every lifecycle call and draws every frame. Anything that blocks it delays the screen.
  • A frame reaches the display through the main thread, the RenderThread, the GPU, and SurfaceFlinger.

The first frame is the first image your app puts on the display

A display shows one still image at a time and replaces it many times per second. Each image is a frame. When you tap an app icon, the app's first frame is the first image that the app drew itself. Android measures the time from the launch request to that frame and calls it time to initial display, or TTID.

A React Native app has a second moment that matters more: the first frame that contains content React rendered. This guide calls it the first React frame. In a bare React Native 0.72 app, the two moments can be hundreds of milliseconds apart, and Android measures only the first one for you. Part 3 shows why, and Part 5 shows how to measure both.

A process is a running program with its own memory and threads

The CPU in your device runs machine code: numbered instructions such as "load this value", "add these two numbers", and "jump to that address". A program is a file that holds machine code. When the operating system runs a program, it creates a process. A process has three parts:

  • An address space: the memory the process can see. The kernel fills it with parts of files and with fresh memory.
  • One or more threads. A thread is one sequence of instructions being executed. The kernel moves threads on and off the CPU cores many times per second, so several threads appear to run at once.
  • Resources: open files, network sockets, and a user ID that decides what the process may access.

Android runs on the Linux kernel. Every Android app runs as its own Linux process, under its own Linux user ID. The kernel stops apps from reading each other's memory and files.

Two kernel facts matter for startup. Reading from flash storage is much slower than reading from RAM, so the kernel keeps recently read file data in RAM, in the page cache. The first launch after a reboot reads everything from flash, and later launches find much of it already in RAM. The kernel can also map a file into a process's address space without reading it, with the mmap system call. The process then reads a 4 KB page of the file only when code touches that page. Hermes relies on this for your JavaScript, as Part 2 explains.

Android creates your process by copying a template process

Three words get mixed up often, so this guide defines them first:

  • An app, or package, is what is installed: one APK file and a private data folder.
  • A process is the running program. Android starts it and stops it. Android does not ask the app first.
  • An Activity is one screen of UI with its own window. Your React Native app has one Activity, MainActivity. React draws all of your screens inside it.

Most Android code is written in Java or Kotlin and compiled to dex bytecode. ART, the Android Runtime, runs that bytecode. Starting ART and loading the Android framework classes takes more than a second, so Android avoids doing it at launch. At boot, a process called zygote starts ART, loads thousands of framework classes, and waits. Every app process is a copy of zygote, made with the Linux fork() call. A forked child shares its parent's memory pages until one of them writes to a page, so the copy is almost instant.

Zygote gives your process a prepared runtime and the common framework classes. It does not preload your app's code, your JavaScript bundle, or React Native. Your process still loads all of those itself.

A second system process, system_server, runs Android's core services, such as the activity manager and the window manager. Apps talk to system_server through Binder, which lets a process call a method on an object that lives in another process. Android names three kinds of start. A cold start has no process yet, so every step in the figure runs. A warm start has a running process but must create the Activity again. A hot start only brings an existing Activity to the front. This guide is about the cold start, because it does the most work.

Key idea

Your process is a copy, not a fresh start. zygote hands you a warm runtime and the framework, but none of your own code: React Native, Hermes, and your bundle all load after the fork.

A display redraws itself on a fixed clock, called vsync

A display is a grid of pixels. It does not hold an image by itself. Many times per second, the display hardware reads an image from a buffer in memory and lights its pixels from top to bottom. This is called scanout, and on a 60 Hz panel it happens every 16.7 ms.

If an app changed that buffer while scanout was halfway down the screen, the top half would show the old image and the bottom half the new one. That artifact is called tearing. To prevent it, the system keeps at least two buffers. The display reads one while apps draw into another, and the system swaps them only in the short gap between two scanouts. That gap is signalled by vsync, short for vertical synchronization.

Android turns that hardware signal into a clock that the whole system follows. Your app's frame work starts on a vsync. SurfaceFlinger combines all windows on a vsync. A new image reaches the glass on a vsync. Anything that is not ready in time waits for the next one, and the display shows the previous image again. Users see that repeat as a stutter, called jank.

Two consequences matter for startup. The first frame of a cold start can appear only on a vsync, so a frame that is ready 1 ms after a vsync waits up to one full period. And a frame drawn now reaches the glass a vsync or two later, after SurfaceFlinger composites it. Neither delay is something your code can remove, but both appear in every measurement.

Key idea

Nothing reaches the glass between two vsyncs. A frame that misses its vsync waits a full period, and the user keeps seeing the old image.

One thread draws, and it follows the display's clock

Every app process starts with one thread, the main thread, also called the UI thread. The main thread runs a loop. A Looper takes the next message from a MessageQueue, runs it to completion, and takes the next one. Lifecycle calls such as onCreate, touch events, and drawing are all messages in the same queue. If one message takes 300 ms, nothing else on the main thread runs for 300 ms, including drawing.

The display refreshes at a fixed rate, and on each refresh the system sends a vsync signal: every 16.7 ms at 60 Hz. On vsync, the Choreographer class runs input handling, animation, measure, layout, and draw, in that order. Draw does not produce pixels. It records a display list, which is a list of drawing commands. A second thread in your process, the RenderThread, turns the display list into GPU commands. The GPU renders into a buffer. SurfaceFlinger, a system process, combines the buffers of all visible windows and sends the result to the display.

React Native adds a thread for JavaScript, named mqt_js. React usually runs there, in parallel with the main thread. Only the main thread can change Android views, so it applies React's finished list of view changes.

For startup, this means the first frame appears after the main thread finishes its first measure, layout, and draw pass, and SurfaceFlinger shows the buffer. Any work that blocks the main thread before that point delays the first frame.

The APK is a zip file, and each part has a different reader

Your app ships as an APK: a zip file with a fixed layout. At startup, a different part of the system reads each part of it.

  • classes.dex holds all Java and Kotlin code: your MainActivity, React Native's Java layer, and the Android code of every library. ART interprets it, compiles hot methods while the app runs (JIT), or uses code compiled ahead of time (AOT). Which one runs at launch depends on how the app was installed and compiled.
  • lib/arm64-v8a/*.so holds native code compiled from C++: Hermes, React Native's C++ core, fbjni (the glue between Java and C++), and the C++ standard library. The dynamic linker loads these files.
  • assets/index.android.bundle holds your whole JavaScript app, already compiled to Hermes bytecode. Part 2 covers it.
  • res/ holds layouts, images, strings, and themes. Your theme decides what the user sees before any of your code runs.
  • AndroidManifest.xml declares the activities, permissions, receivers, and providers. PackageManager reads it at install time.

After the first frame, Android can stop or kill your app at any time

Android moves your Activity between states and calls a method on each transition. The user, the system, and memory pressure decide when, not your code. The callbacks come in pairs:

  • onCreate and onDestroy: the Activity object exists.
  • onStart and onStop: the Activity is visible.
  • onResume and onPause: the Activity is in front and receives input.

React Native passes these to JavaScript: onResume sets AppState to 'active', and onPause sets it to 'background'. Try the events in the simulator.

Three Android behaviours explain most of what the simulator shows:

  • Rotation normally destroys and recreates the Activity. The React Native template prevents that with android:configChanges on MainActivity. Android then calls onConfigurationChanged, and React receives a Dimensions change event.
  • The Android Bundle class is not the JS bundle. It is a small key-value map. Before your Activity goes to the background, Android calls onSaveInstanceState, which writes UI state into a Bundle that system_server keeps. If the process dies, the new Activity receives it in onCreate(savedInstanceState). React state lives in the JavaScript heap and is not saved there.
  • Process death has no callback. lmkd, the low-memory killer, ends processes with SIGKILL, starting with cached background apps. No onDestroy runs. The next launch is a full cold start.

What React Native is, piece by piece

React Native is several separate systems in one Android app. Each one has one job. This part names every piece, says what it does, and explains how the pieces talk to each other.

In short

  • React computes a description of the UI. Fabric turns that description into Android views.
  • Hermes runs your JavaScript from bytecode that was compiled on your build machine.
  • "New Architecture" and "bridgeless" are two separate switches. A 0.72 New Architecture app still builds the bridge.

React describes UI as a function of data

React is a JavaScript library for building user interfaces. You write components: functions that take data and return a description of UI. That description is a tree of plain JavaScript objects called React elements.

function Row({ name, avatar }) {
	return (
		<View style={{ flexDirection: "row", padding: 16 }}>
			<Image source={avatar} style={{ width: 40, height: 40 }} />
			<Text>{name}</Text>
		</View>
	);
}

React does not draw anything. "Rendering" in React means calling your components to calculate a description. It does not mean drawing pixels. React compares the new description with the previous one, a step called reconciliation, and hands a renderer the list of changes. React DOM applies changes to HTML in a browser. React Native's renderer applies them to Android views.

React Native is six pieces with six jobs

Inside your app's process, React Native consists of these pieces:

JSI and JNI are interfaces, not workers. They do not create threads, and they do not run anything in parallel. A JSI call runs on the thread that makes it, and it blocks that thread until it returns.

Fabric and TurboModules solve different problems. Fabric draws the UI. TurboModules give JavaScript access to native capabilities. Your settings app uses Fabric for every row on the screen, and it uses native modules only when it reads something from the device.

Key idea

Interfaces do not create threads. A JSI call runs on the thread that makes it, and it blocks that thread until it returns.

"New Architecture" and "bridgeless" are two separate switches

The bridge is the old runtime plumbing between JavaScript and native code. In the old design, a JavaScript call to a native module was put in a queue as a module ID, a method ID, and a list of converted arguments. The bridge delivered the queue to the native side in batches. Most calls were asynchronous, and a few legacy methods were marked as synchronous.

The New Architecture adds JSI-based systems: Fabric for rendering and TurboModules for native capabilities. It does not remove the bridge by itself. Removing the bridge is a separate step called bridgeless mode.

A JavaScript engine turns text into running code, and Hermes does half the work at build time

A CPU cannot run JavaScript text. A JavaScript engine does the translation. Every engine does four jobs:

  1. Parse. Read the source text and build a tree that represents the program.
  2. Compile. Turn the tree into bytecode: compact instructions for a virtual machine, not for the real CPU.
  3. Execute. Run the bytecode in an interpreter. Many engines also have a JIT compiler that turns frequently run bytecode into machine code while the program runs.
  4. Manage memory. A garbage collector finds objects that the program can no longer reach and frees them.

A browser receives source text, so it parses and compiles on the device. Older React Native apps used JavaScriptCore the same way: on every cold start, the device parsed and compiled the whole bundle before running any of it.

Hermes is a JavaScript engine that Meta built for React Native, and it is the default since React Native 0.70. Its main idea is to move parsing and compiling to build time. The hermesc compiler runs on your build machine and writes bytecode into the APK. On the device, Hermes only loads bytecode and runs it.

  • Hermes can map the bytecode instead of reading it. The bytecode format is designed to be memory-mapped and paged in from flash on demand. Code that never runs is never read, if the file is stored uncompressed.
  • Hermes has no JIT. Meta left it out on purpose, because a JIT needs warm-up time and memory. Startup does not suffer, but JavaScript runs more slowly per operation than compiled Kotlin or C++.
  • Hermes is a library in your process. It is libhermes.so, loaded like any other native library.
Key idea

Hermes reads only the bytecode it runs. A large bundle costs little. A lot of code that runs at startup costs a lot.

The bundle file is your whole JavaScript program, compiled into one file

In React Native, "the bundle" means one file that contains your entire JavaScript program and every JavaScript library it uses. The build produces it in two steps.

Metro, the React Native bundler, starts at index.js and follows every import. It runs each file through Babel, which turns TypeScript and JSX into plain JavaScript and turns import into require. Metro wraps each file in a function, gives it a number, and writes everything into one text file:

bundle.js, simplified, before Hermes compiles it

// prelude and polyfills: console, Promise, error handling
__d(function (global, _$$_REQUIRE, _$$_IMPORT_DEFAULT, _$$_IMPORT_ALL, module, exports, _dependencyMap) {
	var _reactNative = _$$_REQUIRE(_dependencyMap[0]);   // react-native
	var _App = _$$_IMPORT_DEFAULT(_dependencyMap[1]);    // ./App
	_reactNative.AppRegistry.registerComponent("Settings", function () { return _App; });
}, 0, [1, 412]);                    // module 0 is index.js. It depends on modules 1 and 412.

__d(function (…) { /* ./App.tsx */ }, 412, [1, 413, 588]);
// one __d(...) call per module, often thousands of them

__r(0);                             // "require module 0": start the app

Then Gradle runs hermesc on that text file. It compiles the whole program into Hermes bytecode and writes the result to assets/index.android.bundle. The name still says "bundle", but the content is binary. You can check: the file starts with the Hermes bytecode magic number.

xxd -l 8 android/app/build/generated/assets/createBundleReleaseJsAndAssets/index.android.bundle
# 00000000: c61f bc03 c103 191f    ← Hermes bytecode, not JavaScript text

Two things in this structure matter for startup. A module's function runs only when something calls require for it, so the set of modules that run at startup is decided by your import graph. And React Native 0.72 opens the bundle through Android's asset manager: if the APK stores the file compressed, Android inflates the whole file into RAM before Hermes reads it. One cold start, step by step

This part follows a React Native 0.72 cold start through the source code, from the fork to the first React frame. At each step it shows what exists in your process and which thread is doing the work.

In short

  • By the end of Application.onCreate, the 0.72 template has built the React host and loaded Hermes. No JavaScript has run yet.
  • React starts on background threads. The main thread draws an empty frame first, and the React content arrives later.
  • Native setup and your bundle run at the same time on different threads. The first React frame waits for whichever finishes last.

Your process fills up in seven steps

The figure walks through the cold start in seven steps. For each step, it shows the threads, the Java and Kotlin objects, the native code, and the JavaScript heap that exist at that point. Items added in the current step are highlighted.

The steps are a dependency order, not one sequence on one thread. Several of them overlap, as the sections below explain.

Step 2: the process binds the application

After the fork, the main thread runs ActivityThread.main(), starts its Looper, and calls attachApplication. system_server replies with bindApplication. The main thread then opens your APK's dex files with a new class loader and builds your Application object. Before Application.onCreate runs, Android creates every ContentProvider declared in the merged manifest and calls its onCreate. Libraries declare providers too. Many SDKs use one to initialize themselves without any code from you, and each one runs on the main thread before your first frame.

Watch it · scenes 4 and 5

Step 3: Application.onCreate loads most of React Native

This is MainApplication.onCreate in the 0.72 template:

@Override
public void onCreate() {
	super.onCreate();
	SoLoader.init(this, /* native exopackage */ false);
	if (BuildConfig.IS_NEW_ARCHITECTURE_ENABLED) {
		DefaultNewArchitectureEntryPoint.load();
	}
	ReactNativeFlipper.initializeFlipper(this, getReactNativeHost().getReactInstanceManager());
}
  1. SoLoader.init registers the places to look for .so files. It loads no libraries itself.
  2. DefaultNewArchitectureEntryPoint.load() turns on the TurboModule and Fabric flags, then loads libreact_newarchdefaults.so and libappmodules.so. libappmodules links against Fabric, the TurboModule system, JSI, Yoga, folly, glog, and fbjni, so the loader brings all of those in too.
  3. The release version of ReactNativeFlipper.initializeFlipper does nothing. But Java evaluates the argument before the call, so getReactInstanceManager() runs in release builds too, and it builds the ReactInstanceManager right here.

While it builds, the instance manager picks a JavaScript engine. In 0.72.17, DefaultReactNativeHost overrides getJSEngineResolutionAlgorithm() to return HERMES. But ReactNativeHost.createReactInstanceManager() never passes that value to the builder, and the builder's setJSEngineResolutionAlgorithm is private and has no callers. The builder therefore takes its "not set" path: it tries to load JavaScriptCore, catches the failure, and then loads libhermes.so and libhermes_executor.so. You can confirm this on your device:

adb logcat -d | grep "JS Engine Resolution"
# ReactInstanceManagerBuilder: You're not setting the JS Engine Resolution Algorithm.
#   We'll try to load JSC first, and if it fails we'll fallback to Hermes

If the line appears, your app takes the fallback path. Part 6 shows a one-method fix.

Is the empty host loaded?

Yes, and more than an empty host. By the end of Application.onCreate, the 0.72 template has created the ReactNativeHost and a configured ReactInstanceManager, and it has loaded the Hermes library. Nothing is running yet. There is no JavaScript runtime, no bridge, and no JavaScript thread. Those start in MainActivity.onCreate.

Watch it · scene 6

Step 4: MainActivity starts React on a background thread

MainActivity extends ReactActivity, which hands every lifecycle call to a ReactActivityDelegate. In onCreate, the delegate creates a ReactRootView, an empty FrameLayout marked as a Fabric root, and calls startReactApplication on it. Then it calls setContentView(rootView).

Watch it · scenes 7 and 8

startReactApplication calls createReactContextInBackground(). In a release build, that method starts a thread named create_react_context at display priority. The main thread does not wait. It continues with onStart and onResume, adds the window, and draws the Activity's first frame on the next vsync. That frame shows an empty root view. The root view attaches itself to React the first time it is measured.

Step 5: the React context is built on create_react_context

ReactInstanceManager.createReactContext does this, in order:

  1. Creates the Hermes executor object (marker VM_INIT).
  2. Builds the native module registry from every package. A plain ReactPackage returns finished module objects from createNativeModules(), so those modules are constructed now. Provider-based packages register a factory instead.
  3. Builds the bridge, CatalystInstanceImpl. This loads libreactnativejni.so and starts two threads, mqt_js and mqt_native_modules. The Hermes runtime is created on mqt_js while create_react_context waits.
  4. Builds the TurboModuleManager, then constructs each TurboModule marked needsEagerInit, one after another.
  5. Sets up Fabric. This creates the view managers from every package and the FabricUIManager.
  6. Calls runJSBundle(), which reads the bundle asset and queues it to run on mqt_js. The call returns without waiting for the bundle to finish.

Step 6: the bundle runs while native setup continues

When createReactContext returns, React Native posts setupReactContext to the mqt_native_modules thread. So two things now run at the same time:

Watch it · scenes 9 and 10

  • On mqt_js, Hermes runs the bundle: __r(0), then every module that index.js requires, depth-first. Every top-level statement in those modules runs now. At the end, AppRegistry.registerComponent stores your root component in a table. Nothing renders yet.
  • On mqt_native_modules, setupReactContext initializes the native modules that already exist and attaches the measured root view. Attaching the root view starts the Fabric surface. The surface's call into JavaScript is queued behind the bundle, so it runs after registerComponent.

Step 7: React renders, Fabric commits, Android mounts

The queued call runs your root component. React renders, Fabric lays out the result, and the main thread mounts real Android views. When the first child view is added to the root view, ReactRootView.onViewAdded logs the CONTENT_APPEARED marker. That marks the moment the view was added, not the moment a frame was drawn. The next vsync draws it, and SurfaceFlinger presents it after that.

Watch it · scenes 11 and 12

Key idea

Ask one question of every piece of startup work: does the first screen wait for it? If it does, the thread it runs on hardly matters.

The scenarios show two different problems:

  • Main-thread blocking stops the main thread from mounting and drawing content that is ready. Moving work to another thread fixes it.
  • Dependency blocking means the content is not ready to mount yet, because something it needs has not finished. Moving work to another thread does not fix it. Only removing the dependency from the first screen does.

The second problem is the more common one in React Native apps, because so much of the startup chain already runs off the main thread.

React output reaches the screen in three phases: render, commit, mount

  1. Render. React calls your components. For every host component (View, Text, Image), it calls into C++ through JSI to create a shadow node, a C++ object that holds the element's props. Together the nodes form the shadow tree. A shadow node describes layout. It is not a visible view.
  2. Commit. Yoga, a C++ flexbox engine, computes the position and size of every node. Text needs real font measurement, so Fabric calls into Java through JNI and measures the text with Android's text layout.
  3. Mount. Fabric compares the new tree with what is on screen and produces mount instructions: create a view, set its props, insert it, set its frame. The main thread carries them out through view managers.

In the common startup path, render and commit run on the JS thread and mount runs on the main thread. Fabric's threading model also allows render and commit on other threads for some updates. Only the mount step must run on the main thread, because only that thread may change Android views.

Three different frames are all called "the first frame"

  • The starting window is drawn by system_server from your theme before your code runs. The 0.72 template's AppTheme does not set windowBackground, so it shows the default AppCompat background.
  • The Activity's first frame ends TTID. Android starts that clock when system_server handles the launch intent, not when the finger touches the glass. It stops the clock when the Activity's windows report their first drawn frame.
  • The first React frame is the first frame drawn after React mounts content into the root view. Android does not measure it for you.
Know which number you have

In a bare 0.72 app, TTID measures frame 2, which barely depends on JavaScript. A fast TTID can hide a slow first React frame. If a splash-screen library holds the splash until JavaScript hides it, the library delays the Activity's first draw, and TTID then roughly equals the first React frame. That is one reason published React Native startup numbers vary so much.

Native modules: when they are built and where they run

A native module is how JavaScript reaches the device: storage, Bluetooth, your own hardware. On a settings app, they are often the most expensive part of startup. This part explains exactly when React Native builds a module, on which thread, and what "lazy" really buys you.

In short

  • A registered module is not a constructed module. Registration, construction, initialization, and invocation are four separate events.
  • A TurboModule is constructed on the first lookup, on the thread that asks. That is often the JS thread, during your bundle.
  • Lazy helps only if nothing on the startup path asks for the module. React Native never builds modules in parallel for you.

A module goes through four separate events

Keep the four events apart when you read profiles and source code. A registry can know a module's name and how to build it without holding a built module. A module can be built without being used. Only construction and initialization cost startup time, and they happen at different moments depending on how the module is registered.

How @ReactMethod works in a legacy module

Here is a legacy module with one asynchronous method and one synchronous method:

public class DeviceInfoModule extends ReactContextBaseJavaModule {
	DeviceInfoModule(ReactApplicationContext context) { super(context); }

	@Override public String getName() { return "DeviceInfo"; }

	@ReactMethod
	public void readDeviceName(Promise promise) {   // async: mqt_native_modules
		promise.resolve(Build.MODEL);
	}

	@ReactMethod(isBlockingSynchronousMethod = true)
	public String getDeviceNameSync() {             // sync: blocks the JS thread
		return Build.MODEL;
	}
}

That Java method does not become JavaScript. React Native builds a binding that JavaScript can call, in five steps:

  1. When the module registry is built, JavaModuleWrapper uses Java reflection to find the methods annotated with @ReactMethod.
  2. It creates a descriptor for each method: its name and whether it is asynchronous, Promise-based, or synchronous.
  3. The JavaScript side, in NativeModules.js, creates callable stubs from those descriptors. It creates them lazily, when JavaScript first reads NativeModules.DeviceInfo.
  4. Calling an asynchronous stub puts the module ID, the method ID, and the arguments in a queue, which the bridge flushes to native code in batches.
  5. On mqt_native_modules, native code converts the arguments and invokes the Java method. A synchronous method skips the queue and runs on the JS thread.

A TurboModule starts from a typed spec

A TurboModule begins as a TypeScript or Flow specification. Codegen reads it at build time and generates a Java base class and C++ JSI glue:

src/specs/NativeDeviceInfo.ts

import type { TurboModule } from "react-native";
import { TurboModuleRegistry } from "react-native";

export interface Spec extends TurboModule {
	getDeviceName(): string;           // sync: runs on the calling JS thread
	readSerial(): Promise<string>;     // async: dispatched through the native invoker
}

export default TurboModuleRegistry.getEnforcing<Spec>("DeviceInfo");

android/app/src/main/java/com/yourapp/DeviceInfoModule.java

public class DeviceInfoModule extends NativeDeviceInfoSpec {   // generated by Codegen
	public DeviceInfoModule(ReactApplicationContext context) {
		super(context);                                        // runs on the first lookup
	}
	@Override public String getName() { return "DeviceInfo"; }
	@Override public String getDeviceName() { return Build.MODEL; }
	@Override public void readSerial(Promise promise) { promise.resolve(readSerialFromHardware()); }
}

Register it through a provider, so that React Native can build it on demand:

public class DevicePackage extends TurboReactPackage {
	@Override
	public NativeModule getModule(String name, ReactApplicationContext context) {
		return name.equals("DeviceInfo") ? new DeviceInfoModule(context) : null;   // called on first lookup
	}

	@Override
	public ReactModuleInfoProvider getReactModuleInfoProvider() {
		return () -> Collections.singletonMap("DeviceInfo", new ReactModuleInfo(
			"DeviceInfo", DeviceInfoModule.class.getName(),
			false,   // canOverrideExistingModule
			false,   // needsEagerInit: true builds it before the bundle runs
			false,   // hasConstants
			false,   // isCxxModule
			true));  // isTurboModule
	}
}

You cannot tell a module's kind from @ReactMethod alone

Codegen's generated Java base classes also carry @ReactMethod annotations, and TurboReactPackage is a lazy package API that can hold either kind of module. In a bridge-based 0.72 app, TurboModuleRegistry.get() in JavaScript checks the legacy NativeModules table first and falls back to the TurboModule proxy. So a JavaScript spec can resolve to a legacy implementation. To know what you have, check four things:

  1. Does the Java class extend a Codegen-generated Native…Spec class and implement TurboModule?
  2. Does its ReactModuleInfo say isTurboModule = true?
  3. Is it registered through TurboReactPackage (provider) or a plain ReactPackage (built objects)?
  4. Which path does a trace show at runtime? A TurboModule construction appears under the TurboModuleManager. A legacy construction logs CREATE_MODULE_START with the module's name.

Lazy does not mean "after the first screen"

A lazy module is built when something first asks for it. If something on the startup path asks, the module is built on the startup path. This is the most common way a lazy module ends up costing startup time:

// src/settings/deviceName.ts, imported by the first screen
import NativeDeviceInfo from "../specs/NativeDeviceInfo";

export const deviceName = NativeDeviceInfo.getDeviceName();   // runs while the bundle executes

The top-level line runs while the bundle executes. The lookup constructs the module on the JS thread, then calls a synchronous method on the JS thread. The constructor, initialize(), and the call all delay the first React frame, even though the module is "lazy". Move the call to the point of use:

export function useDeviceName() {
	const [name, setName] = useState<string | null>(null);
	useEffect(() => {
		NativeDeviceInfo.readSerial().then(setName);   // after the first render, asynchronous
	}, []);
	return name;
}

Now the first screen renders with a placeholder, and the module is built after the first frame.

Key takeaways

  • For every native module, ask three questions: when is it registered, when is it constructed, and who asks for it first?
  • Plain ReactPackage modules are always built at startup. Move expensive ones to a provider-based package.
  • A lazy module built by a top-level import is startup work on the JS thread.

Build a StartupMetrics module, the way Expo does

Every timestamp in this module uses SystemClock.uptimeMillis(), the same clock as Process.getStartUptimeMillis(). That makes every milestone comparable with process start.

android/app/src/main/java/com/yoursettings/StartupMetrics.java

public final class StartupMetrics {
	private static final Map<String, Long> marks = new LinkedHashMap<>();

	public static synchronized void mark(String name) {
		if (!marks.containsKey(name)) marks.put(name, SystemClock.uptimeMillis());
	}

	/** Call first in MainApplication.onCreate, before anything React Native does. */
	public static void install() {
		mark("applicationOnCreate");
		ReactMarker.addListener((name, tag, instanceKey) -> {
			switch (name) {
				case RUN_JS_BUNDLE_START: mark("bundleStart"); break;
				case RUN_JS_BUNDLE_END: mark("bundleEnd"); break;
				case CONTENT_APPEARED: mark("contentAppeared"); break;
				default: break;
			}
		});
	}

	/** Prints every milestone as milliseconds since the process started. */
	public static synchronized void log() {
		long start = Process.getStartUptimeMillis();
		for (Map.Entry<String, Long> e : marks.entrySet()) {
			Log.i("Startup", e.getKey() + " +" + (e.getValue() - start) + " ms");
		}
	}
}

Call StartupMetrics.install() as the first line of MainApplication.onCreate, and StartupMetrics.mark("firstResume") in MainActivity.onResume. Then add a native module that JavaScript calls when the panes are visible and when the settings are ready:

public class StartupModule extends ReactContextBaseJavaModule {
	StartupModule(ReactApplicationContext context) { super(context); }
	@Override public String getName() { return "Startup"; }

	@ReactMethod
	public void firstReactFrame() { onNextFrame("firstReactFrame", false); }

	@ReactMethod
	public void settingsReady() { onNextFrame("settingsReady", true); }

	private void onNextFrame(String name, boolean fullyDrawn) {
		Activity activity = getCurrentActivity();
		if (activity == null) return;
		activity.runOnUiThread(() -> Choreographer.getInstance().postFrameCallback(frameTimeNanos -> {
			StartupMetrics.mark(name);
			if (fullyDrawn) { activity.reportFullyDrawn(); StartupMetrics.log(); }
		}));
	}
}

The frame callback runs at the start of the next frame, after React has mounted the views. Android then ends TTFD at the frame drawn after reportFullyDrawn(). This is a close approximation of the drawn frame, not the exact presentation time. Perfetto shows the exact frame if you need it.

Detect when both panes are visible and the values are in

The JavaScript side decides when M2 and M3 happen. Mark M2 when both panes have been laid out. Mark M3 when every row that fits in the right pane has its real value. Work out the visible rows from the pane height and your fixed row height, so the check does not depend on scroll events:

const { Startup } = NativeModules;
const ROW_HEIGHT = 56;

export function SettingsScreen() {
	const panes = useRef({ left: false, right: false });
	const [paneHeight, setPaneHeight] = useState(0);
	const [readyIds, setReadyIds] = useState(() => new Set<string>());
	const rows = useRowsFor(selectedCategory);

	const onPaneLayout = (pane: "left" | "right") => () => {
		if (panes.current[pane]) return;
		panes.current[pane] = true;
		if (panes.current.left && panes.current.right) Startup.firstReactFrame();   // M2
	};

	const visibleIds = rows.slice(0, Math.ceil(paneHeight / ROW_HEIGHT)).map((r) => r.id);
	const settingsReady = paneHeight > 0 && visibleIds.every((id) => readyIds.has(id));
	useEffect(() => { if (settingsReady) Startup.settingsReady(); }, [settingsReady]);   // M3

	return (
		<View style={{ flex: 1, flexDirection: "row" }}>
			<CategoryPane onLayout={onPaneLayout("left")} />
			<View style={{ flex: 1 }} onLayout={(e) => { onPaneLayout("right")(); setPaneHeight(e.nativeEvent.layout.height); }}>
				<SettingsList rows={rows} rowHeight={ROW_HEIGHT}
					onValueReady={(id) => setReadyIds((s) => new Set(s).add(id))} />
			</View>
		</View>
	);
}

On Fabric, onLayout fires after the views are mounted and before they are drawn, which is why the native side waits for the next frame. Both Startup methods only record the first call, so later layouts and value updates do not move the milestones.

Lab numbers come from one device. Field numbers tell you what every device sees. These SDKs are maintained, support bare React Native, and do not need Google Play:

  • Sentry React Native: app start from process start to root mount, plus TTID and TTFD for each React Navigation screen with <TimeToFullDisplay record={ready} />. Sentry can be self-hosted.
  • Embrace: cold and warm start spans from process creation to the first rendered frame.
  • Datadog RUM and Bitdrift: launch and time-to-interactive events with dashboards.

Whichever you choose, check its start and end events against the table at the top of this part, and send your own M2 and M3 to it.

Four ways startup measurements go wrong

  1. The tap is invisible. No app-side tool sees the finger. Every app metric starts at the launch intent or at process start. Only START_TIMESTAMP_SOURCE_EVENT on new Android versions, or a high-speed camera, gets closer.
  2. Background starts look like cold starts. A broadcast or a boot receiver can start your process minutes before the user taps. Classify starts (Expo checks the process importance and ApplicationStartInfo), and discard any start that was not launched by the user.
  3. Timeouts look like data. SDKs give up after a deadline, such as 30 seconds for Sentry TTFD. A cluster of identical large values is a timeout, not a measurement.
  4. A held splash screen moves TTID. If a splash library keeps the splash up until JavaScript hides it, TTID includes your JavaScript, and it can no longer be compared with an app that draws an empty root first.

Make it faster: a playbook for a settings app

Build the two-pane screen for a fast first frame

A two-pane settings screen has a natural shape for startup: the left pane never changes size and never scrolls, and the right pane only needs the rows that fit on the screen. Build it to match that shape:

  • Use a plain split view, not a navigator, for the two panes. A permanent drawer would render the whole drawer and pull in the gesture and animation code for a pane that never moves. Make the left pane ordinary Views driven by state, and render the selected category's component directly in the right pane. Add a nested stack inside the right pane only if a category has deeper pages.
  • Do not virtualize the left pane. A fixed list of categories is cheaper as mapped Views than as a FlatList.
  • Render only what fits in the right pane. For fewer than about 40 rows, a ScrollView with mapped rows is simplest. For longer lists, use a FlatList with a fixed row height, getItemLayout, and initialNumToRender set to the number of visible rows plus one. Only those two props change the first render. Large windowSize and batch values compete with your value loading for the JS thread.
  • Load the other categories on demand with getComponent or an inline require when the user selects them.
  • Fetch a category's values in one native call. One call that returns the Wi-Fi name, the Ethernet state, and the VPN state is cheaper than one call per row. Native code can also read them early, during startup on a background thread, and pass them to React as initial properties.
  • Re-render only the rows whose value changed. Give each row its own subscription to a small store, and memoize the rows. One context at the top re-renders both panes for every value.
  • Show cached values at once if they are good enough. Decide whether a last-known value counts as ready for your M3. If it does, settings ready moves to the first React frame.

Render the list without waiting for anything

The first screen should render from data it already has. Every await before the first render is dependency blocking. Three patterns cause most of it in settings apps:

  • Reading preferences before rendering. Render the list with the row titles at once. Fill in values such as the current Wi-Fi name as they arrive. Show a placeholder until then.
  • Native calls at module top level. A top-level call to a native module runs during the bundle and builds the module on the JS thread (Part 4). Move it into an effect.
  • Restoring navigation state. React Navigation's state-persistence pattern renders nothing until the saved state is read from storage. A settings app rarely needs that. If you do, restore it after the first frame.
function WifiRow() {
	const ssid = useWifiName();                       // starts loading in an effect
	return <SettingsRow title="Network" value={ssid ?? "…"} />;
}

Load only what the first screen needs

On Hermes, code that never runs costs almost nothing, as long as the bundle is stored uncompressed. Code that runs costs time. So the goal is not a smaller bundle. The goal is fewer modules running before the first render.

Check what inline requires actually defers

Metro's inlineRequires option is on by default in React Native 0.72. It moves a top-level require to the places where its value is used, so the module runs only when code first touches it. One research agent ran 0.72's Metro (0.76.8) on sample code and found that require() calls and named imports were inlined, but default imports and namespace imports were not. The React Native docs also say that require calls, "but not imports", are inlined. Check your own bundle:

npx react-native bundle --platform android --dev false --entry-file index.js \
	--bundle-output /tmp/main.jsbundle --sourcemap-output /tmp/main.map
grep -n "_\$\$_IMPORT_DEFAULT\|_\$\$_REQUIRE" /tmp/main.jsbundle | head -40

A call at the top of a module's function runs when the module runs. A call inside a nested function runs later.

Register every sub-page with getComponent

<Stack.Screen name="Bluetooth" getComponent={() => require("./pages/Bluetooth").default} />
<Stack.Screen name="Storage" getComponent={() => require("./pages/Storage").default} />

The page's module, and every library it imports, now runs the first time the user opens the page. The lazy option of tab navigators is different. It delays rendering a tab, but a statically imported tab module still runs at startup.

React.lazy defers code but does not split it

React.lazy(() => import("./pages/Storage")) works, but Metro keeps everything in one bundle in release builds. It gives the same deferral as getComponent, plus a loading state that you must design.

Micro-frontends: Re.Pack and Module Federation

Real code splitting needs a different bundler. Re.Pack, from Callstack, replaces Metro with webpack or Rspack. A dynamic import() becomes a separate chunk file, which a native ScriptManager loads into the same JavaScript runtime when needed. Module Federation builds on that: a host app loads mini-apps that separate teams build and deploy independently. That is the micro-frontend model. Re.Pack 5 needs React Native 0.74 or newer. Re.Pack 4.4.1 supports 0.72 but is frozen. Re.Pack's docs advise against local chunks with Hermes bytecode, because performance gets worse.

Recommendation

A settings app does not need micro-frontends. getComponent for every sub-page, lazy native modules, and no waiting before the first render remove almost all sub-page cost from startup. Consider Module Federation only if separate teams must ship sub-pages independently of the APK, and upgrade React Native first.

React Navigation choices that affect startup

  • Use the native stack (createNativeStackNavigator). It uses Android's own screen containers and transitions, so less JavaScript runs per navigation.
  • Keep the first screen's options cheap. Header components and options functions run during the first render.
  • Keep linking configuration small if you use deep links. The container processes it before the first screen.
  • Use freezeOnBlur on pages that keep updating while hidden, such as a live Bluetooth scan. This does not change startup, but it keeps the list smooth when the user comes back.

Native module hygiene

  • Register expensive modules through a provider (TurboReactPackage with ReactModuleInfoProvider), never a plain ReactPackage.
  • Leave needsEagerInit false unless JavaScript truly needs the module before it renders.
  • Keep constructors and initialize() cheap. Open hardware handles when a method is first called, from the page that needs them.
  • Do slow work on your own executor inside asynchronous methods, and resolve the Promise from there.

How long the SysTray leg takes, and why it is not 5 ms

Your estimate of 20 to 30 ms is reasonable. Here is where that time goes, from React Native 0.72's source:

  1. The touch waits for a frame. When the finger lifts, the UI thread builds a touch event and puts it in a staging queue. React Native moves staged events to JavaScript on the next frame callback. That wait is 0 to 16.7 ms at 60 Hz, about 8 ms on average.
  2. JavaScript handles it in two queued jobs. One delivers the event to Fabric's event emitter. A second runs React's responder system, which calls onPress. Each job waits behind any JavaScript that is already running. With an idle JS thread, this costs about 2 to 6 ms.
  3. The native call is queued. A legacy @ReactMethod call goes into the bridge queue, is flushed to native code (immediately if JS has been idle for 5 ms), and runs on mqt_native_modules.
  4. startActivity is a Binder call into system_server. It takes a few milliseconds before it returns.
SysTray's JS threadT0 to the startActivity callT0 to the call returning
Idleabout 5 to 25 ms, median 10 to 15 msabout 12 to 35 ms

These are estimates from the code path, not measurements. Two more delays happen before T0, and no app can see them: the touch controller's own latency (roughly 5 to 20 ms), and the time the finger is down (getEventTime() - getDownTime(), typically 60 to 150 ms for a quick tap). onPress itself has no built-in delay. delayPressIn and the 130 ms minimum press duration affect only onPressIn and onPressOut. Capture T5 to T12 in Settings

This class collects every milestone in Settings, reads SysTray's values from the Intent, and prints the breakdown relative to the tap. It uses FrameMetrics (API 24 and newer, with FIRST_DRAW_FRAME from API 26) to timestamp drawn frames exactly, instead of guessing.

public final class StartupLog {
	private static final Map<String, Double> marks = new LinkedHashMap<>();      // uptime ms
	private static final Map<String, Double> waitForFrame = new LinkedHashMap<>(); // name → requested at
	private static final Map<String, Double> moduleStart = new HashMap<>();
	private static Runnable onSettingsReadyFrame;

	public static synchronized void mark(String name, double uptimeMs) { marks.putIfAbsent(name, uptimeMs); }
	public static void mark(String name) { mark(name, SystemClock.uptimeMillis()); }

	/** First line of MainApplication.onCreate. */
	public static void install() {
		mark("T5 bindApplication", Process.getStartUptimeMillis());
		mark("T6 Application.onCreate start");
		ReactMarker.addListener((name, tag, key) -> {
			double now = SystemClock.uptimeMillis();
			switch (name) {
				case RUN_JS_BUNDLE_START: mark("T9 bundle start", now); break;
				case RUN_JS_BUNDLE_END: mark("T9 bundle end", now); break;
				case CREATE_MODULE_START: moduleStart.put(tag, now); break;
				case CREATE_MODULE_END:
					Double s = moduleStart.remove(tag);
					if (s != null) Log.i("Startup", "module " + tag + " built in " + (now - s) + " ms on "
						+ Thread.currentThread().getName() + " at +" + now);
					break;
				default: break;
			}
		});
	}

	/** In MainActivity.onCreate, before super.onCreate. */
	public static void attach(Activity activity) {
		Intent i = activity.getIntent();
		for (String k : new String[] {"t0_tapUp", "t1_onPress", "t2_startActivity"}) {
			if (i.hasExtra(k)) mark(k, i.getDoubleExtra(k, 0));
		}
		mark("T7 MainActivity.onCreate");
		HandlerThread t = new HandlerThread("frame-metrics"); t.start();
		activity.getWindow().addOnFrameMetricsAvailableListener((w, fm, dropped) -> {
			double start = fm.getMetric(FrameMetrics.INTENDED_VSYNC_TIMESTAMP) / 1e6;
			double end = start + fm.getMetric(FrameMetrics.TOTAL_DURATION) / 1e6;
			if (fm.getMetric(FrameMetrics.FIRST_DRAW_FRAME) == 1) mark("T8 first frame (TTID)", end);
			resolveFrame(start, end);
		}, new Handler(t.getLooper()));
	}

	/** Record "name" at the end of the first frame that starts after requestedAtMs. */
	public static synchronized void markNextFrame(String name, double requestedAtMs, Runnable then) {
		waitForFrame.put(name, requestedAtMs);
		if (then != null) onSettingsReadyFrame = then;
	}

	private static synchronized void resolveFrame(double start, double end) {
		Iterator<Map.Entry<String, Double>> it = waitForFrame.entrySet().iterator();
		while (it.hasNext()) {
			Map.Entry<String, Double> e = it.next();
			if (start >= e.getValue()) {
				mark(e.getKey(), end); it.remove();
				if (e.getKey().startsWith("T12") && onSettingsReadyFrame != null) { onSettingsReadyFrame.run(); print(); }
			}
		}
	}

	public static synchronized void print() {
		double t0 = marks.containsKey("t0_tapUp") ? marks.get("t0_tapUp") : marks.get("T5 bindApplication");
		for (Map.Entry<String, Double> e : marks.entrySet()) {
			Log.i("Startup", String.format("%-32s +%7.1f ms", e.getKey(), e.getValue() - t0));
		}
	}
}

}

  3. SysTray mqt_native_modules: your SysTray.startActivity section and its Binder transaction.
  4. system_server: startActivityInner, MetricsLogger:launchObserverNotifyIntentStarted (T3), and Start proc: com.yoursettings.
  5. Settings: PostFork, ActivityThreadMain, bindApplication, activityStart, Choreographer#doFrame, then RenderThread DrawFrame.
  6. Settings React Native threads: create_react_context, mqt_js, mqt_native_modules, with the RN … sections from Part 5's marker listener.

Perfetto's own timestamps use the boot clock, which counts deep sleep. Emit your T-points as Trace sections so they appear on the timeline, rather than converting uptime values by hand. Perfetto's startup tables (android_startups, android_startup_time_to_display) support Android 11 traces. On Android 11 the TTID frame is matched by a heuristic, because frame timeline data does not exist before Android 12.

The system event log adds a few free timestamps without a trace:

adb logcat -b events | grep -E "am_proc_start|am_proc_bound|wm_activity_launch_time|wm_on_create_called|wm_on_resume_called"
Key idea

Construction time is not cost. A module built in parallel can cost the first frame nothing. One built on mqt_js costs all of it.

Is Bluetooth delaying your first frame? Prove it in four steps

Your first screen shows brightness, which is in the Display category. Bluetooth and Wi-Fi live in a different category. If their native modules are built during startup, they cost time that the first screen does not need. Whether they delay the first React frame depends on where that work runs. Find out in four steps.

Step 1: list every module built before T11

The StartupLog above logs each legacy module's construction, with its duration and thread, from CREATE_MODULE_START and CREATE_MODULE_END. TurboModules do not log these markers. Add a line to each of your own TurboModule constructors, with a stack trace that shows who asked for it:

public BluetoothModule(ReactApplicationContext context) {
	super(context);
	long start = SystemClock.uptimeMillis();
	Trace.beginSection("BluetoothModule.<init>");
	try { adapter = BluetoothAdapter.getDefaultAdapter(); /* … */ }
	finally { Trace.endSection(); }
	Log.i("Startup", "BluetoothModule built in " + (SystemClock.uptimeMillis() - start) + " ms on "
		+ Thread.currentThread().getName(), new Throwable("who asked"));
}

Step 2: classify each module by where its work runs

Built onWhenDelays the first React frame?
create_react_contextBefore the bundle runs: a plain ReactPackage, or needsEagerInityes, by its full cost The bundle cannot start until it finishes.
mqt_jsDuring the bundle: a lazy module that top-level code asks foryes, by its full cost
mqt_native_modulesIn parallel, during context setupsometimes Only if the first screen waits for its result, or if the device has too few CPU cores to run it in parallel.
Any threadAfter T11no It can still delay T12 if the screen waits for it.

Step 3: find out who asks for it

The stack trace from Step 1 shows the native path. A lookup from JavaScript shows TurboModuleManager.getModule on mqt_js. A legacy module built by package processing shows NativeModuleRegistryBuilder on create_react_context. On the JavaScript side, look for anything that touches the module while the bundle runs: a top-level call, a new NativeEventEmitter(NativeModules.Bluetooth) at module scope, or a state store that subscribes to Bluetooth events when it is imported. Any of these builds the module during startup, even if the module is lazy.

Step 4: confirm the cost with an A/B build

The log tells you how long construction took. Only an experiment tells you how much the first frame moves, because work in parallel can overlap. Build a B variant where Bluetooth and Wi-Fi are deferred:

  1. Register their modules through a provider package (TurboReactPackage with a ReactModuleInfoProvider, needsEagerInit false), or temporarily remove the package from getPackages() for the experiment.
  2. Make sure the Display screen's import graph does not reach their JavaScript wrappers. Load the Network and Bluetooth screens with getComponent.
  3. Install A and B, and alternate them for 30 cold starts each, launched from SysTray.
  4. Compare the medians and 90th percentiles of T11 and T12. The difference is what those modules really cost your first frame.

If B is faster, keep the deferral and start the Bluetooth and Wi-Fi hardware when the user opens their category. If B is no faster, the modules were building in parallel off the critical path, and your time is going elsewhere. The trace will show where.

Set up the stack navigator for a fast first screen

On React Native 0.72 with Fabric, use React Navigation 6 with @react-navigation/native-stack and react-native-screens 3.21 to 3.27, which are the 3.x versions that support Fabric on 0.72. The JS stack (@react-navigation/stack) needs react-native-gesture-handler imported at your entry point and builds every card's animation in JavaScript, so it costs more at startup.

Keep the left pane outside the navigator, and give the right pane one native stack that starts on the Display category:

const RightStack = createNativeStackNavigator();
const screenOptions = { headerShown: false, animation: "slide_from_right" };   // a static object

export function SettingsApp({ initialCategory = "Display" }) {
	return (
		<NavigationContainer ref={navRef} onReady={() => Startup.navigationReady(performance.now())}>
			<View style={{ flex: 1, flexDirection: "row" }}>
				<CategoryPane onSelect={(name) => navRef.reset({ index: 0, routes: [{ name }] })} />
				<View style={{ flex: 1 }}>
					<RightStack.Navigator initialRouteName={initialCategory} screenOptions={screenOptions}>
						<RightStack.Screen name="Display" component={DisplayScreen} />
						<RightStack.Screen name="Network" getComponent={() => require("./categories/Network").default} />
						<RightStack.Screen name="Bluetooth" getComponent={() => require("./categories/Bluetooth").default} />
						<RightStack.Screen name="WifiDetails" getComponent={() => require("./categories/WifiDetails").default} />
						{/* every other category and drill-down page the same way */}
					</RightStack.Navigator>
				</View>
			</View>
		</NavigationContainer>
	);
}
  • Import the first screen directly and nothing else. Only DisplayScreen and its imports run before the first frame.
  • Pass the starting category from SysTray as initial properties (read in getLaunchOptions of your ReactActivityDelegate), not through deep linking. With linking set, the container waits for Linking.getInitialURL() before it renders.
  • Do not restore navigation state at startup. State persistence reads storage before the first render.
  • Use static options objects. An options function runs on every render and creates new objects.
  • Consider headerShown: false with your own header. react-native-screens issue #1975 reports lost taps with the native header on Fabric on 0.72, and its fix shipped in versions that need React Native 0.75.
  • Use freezeOnBlur for pages that keep updating while a drill-down covers them, such as a live Bluetooth scan. It does not change startup, but it keeps the drill-down smooth.

Glossary

Activity
One screen of UI with its own window and a lifecycle that Android drives. React Native apps have one, MainActivity.
APK
The installed package: a zip file with dex code, native libraries, assets, resources, and a manifest.
ART
The Android Runtime. It runs dex bytecode with an interpreter, a JIT compiler, or ahead-of-time compiled code.
Binder
Android's mechanism for calling methods on objects in another process.
Bridge
The old channel between JavaScript and native code. It sends batches of module IDs, method IDs, and converted arguments. Still built on 0.72.
Bridgeless
A configuration with no bridge at all. Default for New Architecture apps from 0.74.
Bundle (Android)
A small key-value map that Android uses for saved instance state.
Bundle (JS)
Your whole JavaScript program in one file, compiled to Hermes bytecode, stored in assets/.
Codegen
The build step that turns a TurboModule's typed spec into Java and C++ binding code.
Cold start
A launch with no existing process.
Dependency blocking
The first screen cannot mount because something it needs has not finished, on any thread.
Fabric
React Native's renderer in the New Architecture: a C++ shadow tree, Yoga layout, and mounting to Android views.
First React frame
The first drawn frame that contains content React rendered.
Hermes
React Native's JavaScript engine. It runs bytecode compiled at build time by hermesc.
JNI
Java Native Interface. Connects Java and C++.
JSI
JavaScript Interface. Lets JavaScript call C++ directly, on the calling thread.
lmkd
The low-memory killer daemon. Ends processes by priority when memory runs low.
Metro
React Native's bundler. Turns your source files into one bundle of numbered modules.
mqt_js
The thread that runs JavaScript in React Native 0.72.
mqt_native_modules
The thread that runs asynchronous legacy module methods and context setup in 0.72.
RenderThread
The per-app thread that turns recorded drawing commands into GPU work.
Shadow tree
Fabric's immutable C++ description of the UI, with layout from Yoga.
SurfaceFlinger
The system process that combines every window's buffer and sends the result to the display.
TTID
Time to initial display: from the launch intent to the Activity's first drawn frame.
TTFD
Time to full display: from the launch intent to the frame after reportFullyDrawn().
TurboModule
A native module reached through JSI, with generated typed glue, built on first lookup by default.
vsync
The display's refresh signal. Every 16.7 ms at 60 Hz.
Yoga
The C++ flexbox engine that computes the position and size of every view.
zygote
The pre-started process that every app process is forked from.
